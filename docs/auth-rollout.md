## Шаги по порядку

**1. 🟦 Создать OAuth-приложение Google.**
Google Cloud Console → APIs & Services → Credentials → OAuth client ID (тип Web). В Authorized redirect URIs добавить URL из Supabase (шаг 2). Получить Client ID и Client Secret. (Apple — аналогично, позже.)

**2. 🟦 Включить провайдера в Supabase.**
Supabase → Authentication → Providers → Google → вставить Client ID/Secret, включить. Скопировать оттуда redirect URL обратно в Google (шаг 1). Добавить адрес сайта (GitHub Pages) в Authentication → URL Configuration → Redirect URLs.

**3. 🟩 Экран входа в приложении.**
Кнопка «Войти через Google» → `supabase.auth.signInWithOAuth({ provider: 'google' })`. До входа приложение не пускает в дневник.

**4. 🟩 Сессия в `main.js`.**
В `boot()`: `supabase.auth.getSession()` → если сессии нет, показать вход; если есть, взять `user.id` (uuid) и грузить профиль по нему. Подписаться на `onAuthStateChange`.

**5. 🟦🟩 Миграция идентичности на uuid.**
Схема переходит с `id integer` на `id uuid = auth.uid()`, `user_id` во всех таблицах → uuid. На прототипе данных мало (тестовый юзер) — проще пересоздать таблицы. Я подготовлю миграционный SQL; ты запускаешь его в Supabase SQL Editor.

**6. 🟩 Переписать `db.js`.**
Убрать захардкоженный `userId: 67`. Использовать `auth.uid()` текущего пользователя во всех запросах.

**7. 🟦 Включить RLS.**
Запустить `supabase/enable_rls.sql` в SQL Editor. После этого публичный ключ в браузере больше не даёт доступа к чужим данным — база реально защищена.

**8. 🟩 Обновить ADR-007** (RLS включён) в `decisions.md`.

## Проверка

- Залогинился двумя разными Google-аккаунтами → каждый видит только свои дневник/вес/норму.
- Запрос к таблице без сессии → отклонён (RLS работает).
- `npm run build` и `npm test` зелёные.
